# Архитектурная спецификация: SelfCareMeditation

## 1. Назначение приложения

iOS-приложение для медитаций с дневником самочувствия.
Пользователь: человек, желающий практиковать медитации и отслеживать своё эмоциональное состояние.
Основные действия: просмотр каталога практик, выполнение медитаций, ведение дневника настроения с эмоджи и быстрыми ответами.

---

## 2. Архитектурные зоны и ответственность

### Зона: UI (презентационный слой)

**Отвечает за:**
- Отображение экранов и компонентов
- Навигация между экранами (Expo Router)
- Локальный UI-стейт (React hooks)
- Анимации и визуальные эффекты

**НЕ отвечает за:**
- Бизнес-логику
- Прямые запросы к Supabase
- Хранение глобального состояния

---

### Зона: State (управление состоянием)

**Отвечает за:**
- Глобальное состояние приложения (Redux Toolkit)
- Кеширование данных между экранами
- Синхронизация UI с данными

**НЕ отвечает за:**
- Сетевые запросы
- Персистентное хранение данных
- Бизнес-правила валидации

---

### Зона: Services (сервисный слой)

**Отвечает за:**
- Взаимодействие с Supabase (auth, database, storage)
- Бизнес-логику и валидацию данных
- Трансформацию данных между API и приложением
- Обработку ошибок сетевых запросов

**НЕ отвечает за:**
- UI-логику
- Управление навигацией
- Локальный стейт компонентов

---

### Зона: Types (типизация)

**Отвечает за:**
- TypeScript-интерфейсы и типы
- Контракты между зонами
- Типы для Supabase-таблиц

**НЕ отвечает за:**
- Реализацию логики
- Runtime-валидацию

## 5. Взаимодействие между зонами

### UI → Services

Экраны и компоненты вызывают сервисы через кастомные хуки.
Хуки инкапсулируют логику загрузки, кеширования и обработки ошибок.

```
Компонент → useHook() → Service → Supabase
```

### Services → State

Сервисы возвращают данные в хуки.
Хуки решают: сохранить в локальный стейт (useState) или в глобальный (Redux dispatch).

**Правило:** Redux используется только для данных, которые нужны на нескольких экранах одновременно (например, текущий пользователь, активная сессия медитации).

### State → UI

Глобальный стейт читается через `useSelector`.
Локальный стейт — через `useState` / `useReducer`.

### Граница бизнес-логики

Вся бизнес-логика находится в `src/services/`.
Компоненты и хуки не содержат бизнес-правил — только координацию вызовов.

## 6. Ключевые потоки данных и инварианты

Этот раздел описывает не пользовательский UX и не навигацию,
а устойчивые потоки данных и правила взаимодействия между архитектурными зонами.
Он не фиксирует экраны, маршруты или сценарии использования.

### Поток: Медитативная практика
- Данные: информация о практике, состоянии сессии
- Источник истины: Supabase
- Допустимый путь: UI → hooks → services → Supabase → hooks → UI
- Инварианты:
  - UI не взаимодействует с Supabase напрямую
  - Бизнес-логика обработки практики находится в сервисах
  - Хуки не содержат бизнес-правил

### Поток: Запись дневника самочувствия
- Данные: JournalEntry (настроение, эмоджи, текст)
- Источник истины: Supabase
- Допустимый путь: UI → hooks → services → Supabase → hooks → UI / store
- Инварианты:
  - Валидация и подготовка данных выполняются в сервисах
  - UI отвечает только за ввод и отображение
  - Глобальный стейт используется только при необходимости повторного использования данных

### Поток: Чтение пользовательских данных
- Данные: профиль пользователя, история записей
- Источник истины: Supabase
- Допустимый путь: services → hooks → UI
- Инварианты:
  - Кеширование допустимо, но источник истины остаётся backend
  - UI не содержит логики агрегации данных

### 7. Контролируемые ограничения

### Где должна находиться бизнес-логика

- **Вся бизнес-логика** — в `src/services/`
- **Хуки** — только координация между UI и сервисами
- **Компоненты** — только отображение и обработка пользовательского ввода

### Что нельзя делать по умолчанию

| Запрет | Причина |
|--------|---------|
| Прямые вызовы Supabase из компонентов | Нарушает разделение слоёв |
| Бизнес-логика в компонентах | Усложняет тестирование и переиспользование |
| Глобальный стейт для UI-данных | Redux только для cross-screen данных |
| Хранение секретов в коде | Использовать Expo SecureStore / env-переменные |
| Создание новых папок в корне `src/` | Требует обоснования |

### Что требует осознанного решения

- Добавление новой таблицы в Supabase
- Добавление нового Redux slice
- Создание нового сервиса
- Изменение структуры навигации

## 8. Правила расширения архитектуры

### Когда допустимо добавление новых элементов

| Действие | Условие |
|----------|---------|
| Новый компонент в `components/` | Если переиспользуется или сложен для одного файла |
| Новый хук в `hooks/` | Если логика повторяется в нескольких компонентах |
| Новый сервис в `services/` | Если появляется новая сущность или внешний API |
| Новый slice в `store/slices/` | Если данные нужны на 2+ несвязанных экранах |
| Новая папка в `components/` | Если добавляется новый экран с 3+ компонентами |

### Что должно быть объяснено перед изменением

- Какую проблему решает новый элемент
- Почему существующая структура недостаточна
- Как это влияет на существующие зоны

### Сохранение смысла архитектурных зон

- Новые папки не должны дублировать ответственность существующих
- При расширении — следовать установленным паттернам именования
- Не создавать "особые случаи" — если нужен особый подход, пересмотреть архитектуру

---

## 9. Что можно менять свободно

- Содержимое `src/constants/` (цвета, эмоджи, shortcuts)
- Стили компонентов
- Текстовые строки в UI
- Добавление новых компонентов в существующие папки `components/`
- Добавление новых хуков в `hooks/`
- Добавление новых утилит в `utils/`
- Внутренняя реализация сервисов (без изменения интерфейса)

---

## 10. Что нельзя менять без согласования

| Элемент | Почему |
|---------|--------|
| Структура `app/` (навигация) | Влияет на UX и маршрутизацию |
| Публичные интерфейсы сервисов | Ломает зависимые компоненты |
| Структура Redux store | Влияет на все экраны |
| Схема таблиц Supabase | Требует миграции данных |
| Добавление новых зависимостей | Влияет на размер бандла и совместимость |
| Структура папок в `src/` | Меняет архитектурные границы |
| Этот файл (`architecture.md`) | Является архитектурным контрактом |
